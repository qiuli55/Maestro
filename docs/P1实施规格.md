# Maestro P1 MVP 实施规格（PRD）

> 版本：P1-spec v1.0（2026-08-16）
> 来源：需求文档 v0.4 + 技术方案 v1.2 §8（P1 行）
> 目标：在未上壁纸/数字人外壳前，用命令行证明「拆得开、合得上」核心价值

---

## 1. 目标

在命令行跑通 Orchestrator-Workers 核心链路，并满足 **双场景验收**：

- **场景 A（worker 链路）**：多需求逐个喂 → 串行派发给外部 worker（opencode / octo）→ 各自独立目录执行 → 记录状态，互不干扰
- **场景 B（汇总质量，验收核心）**：3-5 段文本 → 拆 → 并行各读一段 → 汇总成一份统一报告；验收检查点：**无编造**（结论可指回来源段）、冲突被裁决、重复被压缩、遗漏被标记

成功长什么样：`./maestro run --scenario a` 与 `--scenario b` 都能在命令行产出可验证结果，状态落 SQLite，重启可恢复。

## 2. 命令 / 接口

P1 只做命令行入口，不做 Web UI（Web UI 是 P2）。

```
maestro run --scenario {a|b} [--input <path>] [--worker {opencode|octo|embedded}]
maestro status <task_id>            # 查看任务/子任务状态
maestro retry <subtask_id>          # 手动重派失败子任务
maestro reset <task_id>             # 清空重来（开发期）
```

- 输入：场景 A 为需求列表文本（每行一个需求）；场景 B 为多段文本文件
- 输出：stdout 打印最终汇总；`outputs/<subtask_id>/` 落盘各 worker 产出；SQLite 登记 `result_path`
- 配置：`configs/workers.json`（worker 命令路径、工作目录模板、超时）、`configs/prompts.yaml`（拆分/汇总 prompt）、`.env`（DEEPSEEK_API_KEY）

## 3. 结构（模块 / 文件）

```
F:\Maestro\
├─ src/maestro/
│  ├─ db.py            # SQLite 连接 + tasks/subtasks/task_events CRUD，状态机
│  ├─ llm.py           # DeepSeek 封装（split / merge 两次调用），失败重试
│  ├─ workers/
│  │  ├─ base.py       # Worker 接口：spawn(prompt, workdir, timeout) -> (output, error)
│  │  ├─ opencode.py   # opencode run "..." -- 非交互，独立目录
│  │  ├─ octo.py       # octo "..." -- 非交互，独立目录
│  │  └─ embedded.py   # 内嵌：直接调 DeepSeek（仅 LLM 产出+简单文件操作）
│  ├─ split.py         # LLM 拆分 -> subtask 列表（含 worker_type、来源段）
│  ├─ merge.py         # 汇总：来源引用约束 + 冲突裁决 + 去重 + 覆盖扫描
│  ├─ orchestrator.py  # 生命周期状态机：parse→split→dispatch→collect→merge→deliver
│  └─ cli.py           # 命令行入口
├─ configs/            # workers.json / prompts.yaml
├─ tests/              # 单测 + 场景 B 验收样例文本
├─ outputs/            # 各子任务落盘产出（gitignore）
└─ requirements.txt    # fastapi(可选, P1 不启服务) / openai sdk / pyyaml
```

**边界**：编排器唯一中枢；worker 无状态、独立目录；内嵌 worker 只做 LLM 产出+简单文件操作（§4 边界）。

## 4. 代码风格

- Python 3、函数优先、单文件职责清晰（ponytail：够用即止）
- 密钥走 `.env` / 环境变量，绝不进代码或日志
- 测试可读优先（DAMP over DRY）；unittest 或 pytest

## 5. 测试策略

- **单元**：db 状态机、merge 四条规则（来源引用/冲突/去重/覆盖）、split 输出结构
- **集成（场景 B 验收）**：用 `tests/fixtures/b_docs/*.txt`（含人为冲突/重复/遗漏的 3-5 段）跑真实 merge，逐条核对检查点
- **worker 链路（场景 A）**：需 DEEPSEEK_API_KEY + opencode/octo 已装；验证独立目录、stdout 取结果、超时可控、互不干扰
- 覆盖率期望：核心 merge/split/db 有单测保护即可，不强求数字

## 6. 本次不做（边界，防蔓延）

- 壁纸层 / 3D 数字人 / 任务窗口 Web UI（P2-P5）
- WorkBuddy CLI 接入验证（用户要求暂不碰 codex 系；WorkBuddy 自身是否可被命令行驱动留待单独查证）
- DAG depends_on（§3.3 YAGNI：P1 仅串行/并行）
- 语音 STT（MVP 文本输入）
- FastAPI 服务进程（P1 纯 CLI；SQLite 同步访问即可）

## 7. 验收门（对应 §8 P1）

- 场景 A：命令行完成「需求列表 → 逐个投喂 → 串行完成 → 状态记录」，多需求互不干扰
- 场景 B：汇总报告无编造、冲突被裁决、重复被压缩、遗漏被标记（检查点清单见 `tests/fixtures/b_checklist.md`）
