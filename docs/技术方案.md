# Maestro（桌边壁纸 Agent）技术方案

> 版本：v1.2（2026-08-16，评审修订：补全汇总设计、可靠性设计、worker 边界与兜底等，见 §11）
> 配套文档：《需求文档.md》（v0.4）
> 目标：一个嵌在 Windows 壁纸里的多 Agent 编排器 + 写实 3D 数字人

---

## 1. 架构总览

**核心模式：Orchestrator-Workers（业界标准 multi-agent orchestration）**

```
┌─────────────────────────────────────────────────────────┐
│                      桌面 (Windows)                      │
│                                                         │
│  ┌─────────────── 壁纸层（图标层之下）──────────────┐    │
│  │  三态壁纸画面（日常 / 进度全景 / 结果）           │    │
│  │  ┌──────────────────────────────────────┐        │    │
│  │  │  3D 数字人（Three.js 写实模型）        │        │    │
│  │  │  表情 / 口型 / 语音 / 闲聊             │        │    │
│  │  └──────────────────────────────────────┘        │    │
│  └───────────────────────────────────────────────────┘    │
│                                                         │
│  ┌─────────────── 任务窗口（普通小窗，可开关）─────┐    │
│  │  子任务列表（可编辑）/ 进度 / 汇总结果 / 对话记录 │    │
│  └───────────────────────────────────────────────────┘    │
│                                                         │
│  ┌─────────────── Orchestrator 编排器（本机进程）────┐   │
│  │  接收任务 → 拆分 → 派发 → 收集 → 汇总            │   │
│  │  SQLite 状态库 + WebSocket 实时推送               │   │
│  └───────────────────────────────────────────────────┘    │
│         │ 派发子任务（subprocess CLI）                      │
│  ┌──────┴───────┬───────────────┬──────────────────┐       │
│  │ 自己(内嵌)   │  WorkBuddy    │     Codex        │       │
│  │ 轻代码/汇总  │  工具类任务   │   重代码任务      │       │
│  └──────────────┴───────────────┴──────────────────┘       │
└─────────────────────────────────────────────────────────┘
```

**设计原则：**
- Orchestrator 是唯一中枢，负责一切决策（拆不拆、派给谁、怎么合）；Workers 是无状态的执行者
- **汇总与拆分同等重要**：拆分解决「单 agent 上下文超载」，汇总解决「多段结果合回一份可信、完整、无冲突的统一结论」——合不上等于白拆
- Workers 通过 CLI 以子进程方式驱动（业界标准做法，与 OpenAI Codex CLI、Claude Code CLI 同思路）
- 所有状态落 SQLite（任务、子任务、日志、产出），重启可恢复

## 2. 技术栈选型

| 模块 | 选型 | 理由 |
|---|---|---|
| 编排器核心 | **Python 3 + FastAPI** | 用户熟悉 FastAPI；AI 生态最全（langchain/openai sdk 都在 Python）；后续可转商业 |
| 任务状态 | **SQLite** | 零部署、单机够用、后续可平滑迁 PostgreSQL |
| 壁纸/窗口 UI | **Web 前端（HTML/JS + Three.js）** | 渲染数字人必须 WebGL；壁纸层本质是"一个贴桌面的浏览器窗口" |
| 壁纸宿主 | **Tauri（Rust 壳）或 C# 壳** | 极小体积挂到壁纸层；备选 Electron（体积大但生态熟）；**P3 先用最省事方案验证原理（见 §5）** |
| 3D 数字人 | **Three.js + ReadyPlayerMe 模型** | RPM 免费生成写实头像（glTF 带表情 morph target），Three.js 渲染成熟 |
| 语音 TTS | **edge-tts（免费）起步，Azure TTS（付费）进阶** | edge-tts 零成本验证；Azure 提供 Viseme 口型事件，效果最好 |
| 口型同步 | **Viseme 映射**（TTS 事件驱动） | 写实级正确做法；备选音频能量估算（粗糙但免费） |
| 闲聊大脑 | **DeepSeek API（便宜）+ 人格 Prompt** | 与用户已有技术栈一致（Lexi 项目即用 DeepSeek） |
| 实时推送 | **WebSocket** | 任务进度实时刷新到壁纸/任务窗口 |
| 子 agent 驱动 | **subprocess 调 CLI** | WorkBuddy CLI / Codex CLI（codex exec），见 §4 |

**为什么不用商业数字人 SDK（腾讯智影/火山）**：自用起步成本高、绑定平台、不透明；Three.js + RPM 自主可控、能写进简历展示技术深度。商业化时可再评估 SDK 口型/渲染质量。

## 3. Orchestrator 编排器设计

### 3.1 任务生命周期

```
user_task (长任务)
  → parse: LLM 判断是否需要拆分
  → split: LLM 产出子任务列表 [{id, desc, worker_type, depends_on}]
  → dispatch: 并行派发给各 worker（subprocess CLI，独立工作目录）
  → collect: 收集各 worker 产出（stdout / 产出文件）
  → merge: LLM 汇总为最终结果（子任务多时分层汇总；去重 / 裁决冲突 / 覆盖扫描）
  → deliver: 数字人口头汇报 + 任务窗口展示
```

### 3.2 核心数据结构（SQLite）

```
tasks         (id, user_prompt, status, result, result_path, created_at)
subtasks      (id, task_id, desc, worker_type, status, output, error, result_path)
task_events   (id, task_id, subtask_id, ts, event)   -- 供前端实时推送
```

- `result_path`：每个任务/子任务的产出落盘路径（`outputs/<subtask_id>/`），入库登记，重启后也能找到产出在哪
- 状态字段：`pending / running / done / failed / retry`

### 3.3 拆分策略（防幻觉的上半场）

- 按**语义/结构**拆：聊天记录按时间段、长文档按章节、项目按模块
- 依赖声明：`depends_on` 支持 DAG（A 完成后 B 才能开始，如"先读 A 段再做全局总结"）
- **拓扑（YAGNI 约束）**：P1 只实现「串行 / 并行」两种派发拓扑；DAG 依赖图等真实需要时再扩展，不提前做
- 防溢出：每个子任务的输入控制在模型上下文安全区（如单段 < 8k tokens）

### 3.4 汇总策略（防幻觉的下半场，核心价值）

- 子任务 ≤ 5 个：一次 LLM 汇总
- 子任务 > 5 个：分层汇总（先 5 个一组合，再合并组合结果）
- **来源引用约束（核心）**：每个子任务输出必须带来源标记（段号 / 行号 / 文件名）；汇总 prompt 强制「只准引用子结果原文，不得编造子结果中不存在的信息」——这是防汇总幻觉的关键
- **冲突裁决**：两个子结果矛盾时，不直接让 LLM 重写——把双方观点 + 各自来源原文一起交给 LLM 裁决，输出「冲突点 + 双方证据 + 结论」；无法裁决的标记为存疑项，交给用户在任务窗口确认
- **去重**：多段重复叙述同一事实时压缩为一条，保留最早 / 最完整的来源引用
- **覆盖扫描**：拆分清单与汇总结果比对，发现「没有任何子任务覆盖」的内容（拆分遗漏），单独标记提醒

### 3.5 可靠性设计（超时 / 重试 / 失败）

- **超时**：单 worker 执行超时上限（默认可配，如 10 分钟），超时即标记失败并回收进程
- **重试**：失败子任务自动重试 1 次；重试仍失败 → 标红，可在任务窗口手动重新派发
- **失败隔离**：单个子任务失败不影响其他并行子任务收尾；汇总时对失败子任务给出「该段缺失」标记
- **重启恢复**：进程崩溃后，依据 SQLite 状态恢复未完成任务，已完成的产出不重复执行

## 4. Worker 接入方式（命门）

| Worker | 驱动方式 | 说明 |
|---|---|---|
| 自己（编排器内嵌） | 直接调 LLM API | 轻代码：检查、运维、小改动；不产生子进程 |
| WorkBuddy | `workbuddy CLI`（待验证具体命令） | 需要查证 WorkBuddy 的 CLI 调用方式；备选：通过 MCP 协议调用 |
| Codex | `codex exec "<prompt>"` | OpenAI 官方非交互模式，stdout 返回结果，支持指定模型/工作目录 |
| 扩展（Claude 等） | `claude -p "<prompt>"` | 预留适配器接口，worker_type 注册制 |

**P1 第一验证项（命门）：确认 WorkBuddy 能否被命令行驱动。**
- 若能 → subprocess 直调（优先路径）
- 若只有 MCP/API → 编排器作为 client 接入
- **兜底（P1 就做，不等 P6）**：`codex exec` 同步验证；两者都不可用 → P1 退回「内嵌 worker + 文本接口」，外部接入后置
- **验收口径**：P1 只要「至少一个外部 worker 可驱动」即算过，不绑定 WorkBuddy 单一成功路径

**内嵌 worker（自己）边界**：只承担「LLM 产出 + 简单文件操作」（读文件、输出文本/补丁）。需要执行命令、跑测试、复杂重构的子任务一律派给外部 worker——编排器保持轻量，不内置完整 agent 循环。

每个 worker 在**独立工作目录**运行（避免并发写文件冲突），产出物落盘到 `outputs/<subtask_id>/` 并登记 `result_path`。

## 5. 壁纸层实现

**原理（Wallpaper Engine 同款）：**
- Windows 桌面层级：`Program Manager (Progman)` → 壁纸窗口 `WorkerW`（图标层之下）
- 做法：创建宿主窗口 → `FindWindow("Progman")` → 发 `SPI_SETDESKWALLPAPER` 触发 WorkerW 生成 → `SetParent(宿主窗口, WorkerW)` → 宿主窗口铺满屏幕
- 宿主窗口内嵌 WebView（渲染 Three.js 数字人 + 壁纸画面）

**三态壁纸：**
1. **日常态**：正常壁纸画面（数字人站/坐在其中，有呼吸/待机动画）
2. **任务态**：画面切换为子任务进度全景（每个子任务一个节点，实时更新）
3. **结果态**：展示汇总摘要，数字人口头汇报

**点击穿透规则**：壁纸窗口在图标层之下，整窗捕获鼠标会挡住桌面交互。仅数字人所在区域（或任务态进度区）捕获鼠标事件，其余区域鼠标穿透到桌面。

**交互**：点击/对话数字人 → 呼出任务窗口（普通窗口，可开关，不占壁纸层）

**语音输入**：MVP 阶段对话提交用文本输入（任务窗口打字），语音输入（STT）列为可选扩展，不在 MVP 范围内。

**壳选型路径（P3）**：Tauri（Rust）/ C# 都有语言门槛。P3 先用最省事方案验证「WorkerW 挂载 + WebView 渲染」原理（Electron 或 pywebview 小 demo，半天），原理通了再定正式壳。

## 6. 3D 数字人方案

| 环节 | 方案 | 成本 |
|---|---|---|
| 模型 | ReadyPlayerMe 生成写实头像（.glb，带 50+ morph target） | 免费（个人） |
| 渲染 | Three.js（WebGL），加载 glb，morph target 驱动表情 | 免费 |
| 待机动画 | 呼吸、眨眼、微转头（Three.js 时间轴或小动画） | 自研 |
| 语音 | edge-tts（免费，中文好）→ Azure TTS（付费，Viseme 事件） | 0 元起步 |
| 口型 | Viseme 驱动 morph target（准确）；备选音频能量估算（免费粗效） | 自研 |
| 闲聊 | DeepSeek API + 人格 System Prompt（朋友人设、情绪、记忆） | ~¥0.5/百万token |
| 记忆 | 闲聊记录存 SQLite，最近 N 轮作为上下文 | — |

**写实感关键点**：模型用 RPM 高真实度档位；灯光（三点布光）；口型用 Viseme 而非简单张嘴；加头部微动与视线跟随鼠标（沉浸感强，成本低）。

**人格统一**：闲聊（朋友人设）与汇报（工作语气）两套语境并存。定义统一人格基线（System Prompt 底座）+ 工作/闲聊两种模式切换，避免「人格分裂」。

**性能（P4 第一件事）**：加载单模型测帧率，低配机不达标就降面数 / 简化渲染，仍不行降级 Live2D（放弃写实）——不恋战。

## 7. 任务窗口

- 独立普通窗口（可关闭/重开，托盘可唤回）
- 内容：子任务列表（状态：待派发/执行中/完成/失败）、每任务耗时、汇总结果、与数字人的完整对话记录
- **用户干预入口**：拆分子任务列表允许用户编辑（增删改 / 调序 / 标记跳过）后确认执行——LLM 拆分可能拆错，人工闸门是防幻觉最后一道保险
- 失败子任务标红，可手动重新派发
- 与壁纸层通过 WebSocket 同源同步

## 8. 分阶段实施计划

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **P1 MVP（先跑通核心）** | Orchestrator + SQLite；worker 接入（WorkBuddy 优先，Codex 兜底同步验证）；**双场景验收**：A. 多需求逐个喂（串行队列，验证 worker 链路）；B. 长内容分析（3-5 份文本 → 拆 → 并行 → 汇总成统一报告，验证 merge 质量） | A：命令行完成「需求列表 → 逐个投喂 → 串行完成 → 记录状态」，多需求互不干扰；B：汇总报告**无编造**（每个结论可指回来源段）、冲突被裁决、重复被压缩、遗漏被标记 |
| **P2 任务窗口** | Web UI + WebSocket 推送，任务/子任务/进度可视化 + 子任务列表可编辑 | 窗口中实时看到子任务执行过程，可编辑子任务后重派 |
| **P3 壁纸层** | 先用最省事方案验证 WorkerW 原理，再定壳；宿主窗口挂 WorkerW，三态壁纸 + 点击穿透 | 壁纸真实常驻桌面，图标不遮挡，仅数字人区域可点击 |
| **P4 数字人** | RPM 模型 + Three.js 渲染 + 待机动画 + 闲聊（先测帧率，不达标降级） | 数字人站壁纸里，能聊、能汇报 |
| **P5 语音口型** | edge-tts + Viseme 口型 + 视线跟随 | 数字人开口说话，口型对得上 |
| **P6 扩展/打磨** | 接入 Codex CLI 重代码、DAG 依赖、读超长文本拆分汇总、稳定性、商业化评估 | 自用稳定；多 worker 可用；商业化可行性结论 |

**P1 是命门**：先验证「拆得开、合得上」的核心价值（A 验证拆+派，B 验证合），再谈好看的外壳。**汇总质量（场景 B）是 P1 验收的核心，不是可选项。**

## 9. 风险与备选

| 风险 | 影响 | 备选 |
|---|---|---|
| WorkBuddy 无公开 CLI | Worker 接入受阻 | **codex exec 同步验证兜底（P1 就做）**；或 MCP client 方式接入；P1 验收口径不绑定单一 worker |
| 汇总幻觉（子结果之间脑补） | 汇总结果不可信 | §3.4 来源引用约束 + 冲突裁决 + 覆盖扫描 |
| 拆分质量不稳定 | 拆得不好防不了幻觉 | 拆分 prompt 迭代 + 强制拆分规则配置 + **任务窗口人工编辑子任务（§7）** |
| 写实模型性能（低配机） | 数字人卡顿 | 降低模型面数 / 简化渲染；备选 Live2D 降级（放弃写实） |
| edge-tts 口型精度低 | 口型对不上 | 升级 Azure TTS Viseme；或接受"能量估算"粗效果 |
| 壁纸层兼容性（多显示器） | 只铺主屏 | 初期只支持主屏，后续扩展 |
| 壁纸整窗捕获鼠标 | 挡住桌面交互 | 点击穿透规则：仅数字人区域捕获（§5） |
