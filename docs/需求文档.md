# Maestro（桌边壁纸 Agent）需求文档

> 版本：v0.4（2026-08-16，第四轮：评审修订，明确「汇总」为核心价值）
> 状态：需求已确认 + 评审修订完成，技术方案见《技术方案.md》（v1.2）

---

## 1. 产品一句话

一个嵌在 Windows 桌面壁纸里的「多 Agent 总指挥」：以写实级 3D 数字人形象常驻桌面，把长任务拆成短任务、按能力分派给不同 agent 工具（WorkBuddy / Codex 等）执行，**再把各段结果汇总成一份统一交付**；数字人可像朋友一样闲聊。

核心不是「拆」，是「拆得开、合得上」——完整 Map-Reduce 链路。

## 2. 核心动机（为什么做）

1. **防幻觉**：单个 agent 处理超长输入（如一整年聊天记录）时，上下文窗口被塞满、注意力稀释，后期产生幻觉（遗忘早期信息、输出不一致）。拆短后每个子 agent 只专注一小段，上下文干净，输出稳定。
2. **能力组合**：不同 agent 各有所长（WorkBuddy 工具生态强、Codex 代码能力强），按能力分派 1+1>2。
3. **陪伴感**：写实级数字人常驻桌面，像朋友一样可闲聊，让"壁纸"有灵魂。

本质是 Map-Reduce（分而治之）思想在 LLM 上的应用。**Reduce（汇总）与 Map（拆分）同等重要：拆分解决「单 agent 上下文超载」，汇总解决「多段结果合回一份可信、完整、无冲突的统一结论」。** 只拆不合是队列工具，合得上才是 Maestro。

## 3. 角色分工

| 角色 | 职责 | 备注 |
|---|---|---|
| **编排 Agent（壁纸数字人）** | 接任务、拆分、按能力分派、汇总结果；自己处理轻代码任务（代码检查 / 运维 / 小改动）；陪用户闲聊 | 产品核心 |
| **WorkBuddy** | 工具生态类子任务（联网搜索、文档处理、连接器等） | 执行者 |
| **Codex** | 重代码子任务（大模块、复杂实现） | 执行者 |
| **其他 Agent（预留）** | 按需接入（如 Claude） | 可扩展 |

## 4. 核心流程

```
用户向数字人丢来一个长任务
    ↓
编排 Agent 理解任务、拆分
    ↓
按能力分派（并行执行）
    ├─ 自己：轻代码任务（检查 / 运维 / 小改）
    ├─ WorkBuddy：工具生态类任务
    └─ Codex：重代码任务
    ↓
汇总 Agent 收集各 agent 产出（去重 / 裁决冲突 / 覆盖检查）
    ↓
数字人口头汇报 + 任务窗口展示最终结果
```

## 5. 产品形态（已确认）

**三件套，共处一个桌面：**

1. **壁纸（底层舞台）**
   - 整张壁纸就是 agent 的界面层，无卡片、无悬浮挂件
   - 平时是正常壁纸画面，任务进行时切换为子任务进度全景
   - 技术实现：窗口挂到桌面图标层之下（Wallpaper Engine 同款做法）

2. **3D 数字人（壁纸画面内）**
   - **写实级 3D 人像**（非卡通，类似虚拟主播/数字人主播级别）
   - 站/坐在壁纸画面里，是交互入口：说话、点击即可派任务
   - **可像朋友一样闲聊**，有情绪反应，能汇报进度

3. **任务窗口（独立小窗，可开关）**
   - 悬浮于桌面的独立窗口，用户可选择打开或关闭
   - 展示：拆分的子任务列表、每个子任务的进度、汇总结果、长对话记录

## 6. 功能需求（初步）

- [ ] 长任务输入：通过数字人对话 / 任务窗口提交
- [ ] 任务拆分：编排 agent 自动把长任务拆成若干短任务
- [ ] 能力分派：按任务性质分派（自己 / WorkBuddy / Codex）
- [ ] 并行执行：多个子 agent 独立处理各自片段
- [ ] 结果汇总：收集产出合并（子任务过多时分层汇总）
- [ ] **汇总可信度**：汇总结果可追溯来源（每个结论能指回原片段）；子结果冲突时明确裁决，不掩盖矛盾
- [ ] 自写代码：编排 agent 具备轻代码能力（检查 / 运维 / 小改动）
- [ ] 写实级 3D 数字人：常驻壁纸、可互动、可闲聊、有情绪
- [ ] 任务窗口：可开关，展示子任务进度与汇总结果，**允许用户编辑子任务列表（增删改 / 调序）后确认执行**
- [ ] 壁纸三态：日常画面 / 任务进度全景 / 结果展示

## 7. 典型场景

- **长内容分析（MVP 核心场景）**：3-5 份文档 / 一整年聊天记录 → 按时间段 / 章节拆分 → 各 agent 各读一段 → 汇总成一份完整、有来源标注的分析报告
- **多需求逐个喂（P1 辅助场景）**：一次提多个需求（如加登录/加支付/加报表），拆成独立子任务，逐个投喂 WorkBuddy，完成一个再喂下一个——每个子任务独立上下文，不互相干扰（此场景无汇总需求，用于验证 worker 接入链路）
- 大项目并行开发（拆模块 → Codex 并行写 → 汇总合并）
- 长文档阅读理解（拆章节 → 各读各章 → 汇总要点）
- 平时无聊时跟数字人闲聊

## 8. 已决策事项（2026-08-16 第三轮确认 + 第四轮修订）

1. **技术栈**：由技术方案推荐确定（见《技术方案.md》），用户无强偏好
2. **调度方式**：按业界标准 multi-agent orchestration 实现（Orchestrator-Workers 模式），参考 OpenAI Swarm / LangGraph 等成熟范式
3. **数据来源**：暂不设计（聊天记录仅为示例场景，不代表真实输入方式）
4. **产品定位**：先自用，后续可能商业化（商业化诉求后期再评估）
5. **3D 数字人**：写实级人像、可像朋友一样闲聊、带情绪反应、可汇报进度
6. **任务窗口**：独立小窗，可开关，展示子任务进度 / 汇总结果 / 对话记录
7. **（第四轮）汇总与拆分同等重要**：MVP 必须验证完整「拆 → 执行 → 合」链路，汇总质量是验收核心
8. **（第四轮）P1 双场景验收**：场景 A 验证 worker 接入（逐个喂）；场景 B 验证汇总质量（多段 → 统一报告）

## 9. 实施思路（初步建议）

- **MVP 优先**：先做「调度程序 + 命令行驱动子 agent + 文本任务」，验证拆分 / 分派 / **汇总**链路
- **数字人后置**：调度跑通后，再上壁纸层与 3D 数字人（分两步：先静态形象 + 文字对话，再语音 + 口型）
- 拆分规则、汇总策略在 MVP 里用最简单实现，跑通再迭代
