# 第一部分：Anthropic 多 Agent 研究系统

## 1. 他们为什么做多 Agent

Anthropic 的 Claude Research（研究功能）是纯多 Agent 架构，动机很直接：

- **研究是开放性问题**：无法预先把路径写死，要边走边决定下一步——这天然不适合单次线性管线
- **搜索本质是压缩**：从海量网页里提炼洞见。子代理各自用独立上下文并行探索不同方向，把最重要信息"压缩"后返回给主导代理

**性能量化结果（内部评估）**：
> 多 Agent 系统（Opus 4 主导 + Sonnet 4 子代理）比单 Agent（Opus 4）**高出 90.2%**

例子：找 S&P 500 里所有 IT 公司的董事会成员——多 Agent 拆任务给子代理成功完成，单 Agent 因串行搜索太慢而失败。

**关键洞察：Token 用量是性能的第一驱动因素**
BrowseComp 评估中，三个因素解释了 95% 的性能差异：
| 因素 | 解释的方差 |
|---|---|
| Token 使用量 | **80%** |
| 工具调用次数 | 少量 |
| 模型选择 | 少量 |

也就是说：**多 Agent 架构本质是在为"超出单 Agent 限制的任务"扩展 token 用量**——拆任务让每个代理都在自己的上下文里充分思考，而不是挤在一个塞满的上下文里糊弄。

## 2. 系统架构：Orchestrator-Workers

```
用户查询
  ↓
主导代理（Orchestrator）
  ├── 分析查询、制定策略
  ├── 把计划存进外部记忆（Memory）← 上下文超 20 万 token 会被截断，计划必须持久化
  ├── 并行创建多个子代理（Subagent）→ 各自独立 Web 搜索
  ├── 汇总子代理结果，判断够不够；不够就再建子代理或调整策略
  ↓
研究结束后
  ↓
引文代理（CitationAgent）→ 给每个结论补上出处
  ↓
最终结果返回用户
```

**三个角色的职责：**
- **主导代理**：策略 + 拆任务 + 汇总 + 判断是否继续。它是唯一"有全局观"的代理
- **子代理**：迭代搜索，作为"智能过滤器"——把海量搜索结果压缩成最相关信息。用**交错思考**：工具结果回来后先评估质量、找缺口、再优化下一步查询
- **引文代理**：全部研究完，逐条核对声明有来源

**与传统 RAG 的区别**：RAG 是"一次检索相似 chunk 就生成"；这里是"多步动态搜索——边发现边调整策略"。

## 3. 关键设计决策与权衡（血泪教训）

### Token 成本（必须正视）
- Agent 比聊天多耗 **约 4×** token
- 多 Agent 系统比聊天多耗 **约 15×** token
- **结论：任务价值必须够高，才值得为性能买单**

### 延迟与并行化
早期串行搜索极慢 → 引入两类并行：
1. 主导代理一次并行启动 3-5 个子代理
2. 子代理内部并行用 3+ 个工具
> 效果：复杂查询研究时间**最多缩短 90%**

### 同步 vs 异步
当前用同步（等每组子代理全完成再继续）。同步简单但主导代理无法中途干预、子代理间无法协调。
异步并行度更高，但结果协调、状态一致性、错误传播都更难。

### 模型选择
> **升级模型比加大 token 预算更划算**——模型是 token 使用效率的"大乘数"。

### 什么时候不该用多 Agent（重点！）
- 需要所有代理共享同一上下文的任务
- 代理间大量依赖的任务
- **大多数编码任务**：可并行化的部分少，且 LLM Agent 在实时协调和委派方面还不够擅长 ← 这条对你项目很关键
- 低价值任务：15× 的 token 成本划不来

## 4. 任务拆分与汇总（对你最有用的部分）

### 拆任务的坑：指令太模糊 = 子代理各自瞎干
早期版本给子代理"研究半导体短缺"这种一句话指令，结果：
- 子代理误解任务
- 多个子代理执行**完全相同的搜索**（一个查 2021 芯片危机，两个重复查 2025 供应链，没有分工）

**正确做法：每个子任务必须带完整上下文**
- **目标**（objective）
- **输出格式**（output format）
- **工具和来源使用指导**（guidance on tools and sources）
- **明确的任务边界**（task boundaries）

### 任务规模分级规则（直接抄进 prompt）
| 任务复杂度 | 所需 Agent 数 | 工具调用次数 |
|---|---|---|
| 简单事实查找 | 1 个 | 3-10 次 |
| 直接比较 | 2-4 个子代理 | 每个 10-15 次 |
| 复杂研究 | 10+ 个子代理 | 明确分工 |

### 汇总技巧
- 子代理是"智能过滤器"：压缩后返回，别把原始海量结果全倒回来
- 分层汇总：先小组合并，再合并小组结果（防汇总代理上下文又爆掉）

### 进阶模式：子代理把输出写文件系统
子代理把完整产出存到外部文件，只把**轻量引用**传回协调者。好处：
- 防止多阶段"传话游戏"信息丢失
- 减少在对话里复制大段输出的 token 开销
- 特别适合结构化输出（代码、报告）

> **这条和你的项目天然契合**：你的子 agent（Codex/WorkBuddy）本来就该各自写文件到独立工作目录，只把摘要传回编排器。

## 5. 踩过的坑速查表

| 问题 | 解法 |
|---|---|
| 有足够结果还继续搜 | prompt 里写明确停止条件 |
| 搜索词过长 | "先宽后窄"：短而宽的查询起步，逐步缩小 |
| 选错工具 | 给启发式规则：先看全部工具，匹配意图，优先专用工具 |
| 任务描述模糊导致重复劳动 | 每个子代理给详细任务描述（目标/格式/工具/边界） |
| 不知道投入多少合适 | prompt 里嵌入规模分级表 |
| 工具描述差导致跑偏 | 每个工具写清目的和用法；可让工具测试代理先试一遍工具、重写描述（任务时间降 40%） |
| 评估：路径多变没法按流程评 | 基于**结果**而非过程评估；用 LLM-as-judge 打分 |
| 早期总选 SEO 内容农场 | prompt 加来源质量启发式：优先权威但排名低的来源 |
| 长任务状态累积、错误累积 | 持久化执行、错误恢复、从断点继续而非重来；重试 + 定期检查点 |
| 上下文超限 | 智能压缩：总结已完成阶段存外部记忆，新开子代理保持连续性 |
| 部署时新旧版本混跑 | "彩虹部署"：新旧并行、逐渐切流量，别打断正在跑的 Agent |

## 6. 构建多 Agent 系统的最佳实践清单

1. **立即开始小评估集**：约 20 个真实查询就能发现问题（提示微调可能把成功率从 30% 提到 80%）
2. **LLM-as-judge 可规模化评估**：一次调用输出 0-1 分 + 通过/失败
3. **人工评估不可替代**：专抓边界情况
4. **提示工程是最大改进杠杆**：目标是建立好的启发式规则，不是僵化规则
5. **先模拟后上线**：用 Console 观察 Agent 逐步行为
6. **端状态评估**：改状态的 Agent 评估最终状态而非过程
7. **子代理写文件**：减少信息损失和 token 开销

> 核心结论：**"构建 AI Agent 时，最后一英里往往是旅程的大部分。"** 原型到生产差距很大，错误会复合放大。成功靠：细致的提示和工具设计 + 好启发式 + 可观测性 + 快速反馈闭环。

# 第二部分：OpenAI 构建智能体实践指南

## 1. 什么是 Agent（严格定义）

> **Agent 是代表你独立完成任务的系统。**

判断标准：
- 用 LLM **管理整个工作流的执行**并做决策
- 能识别工作流**何时完成**，必要时主动纠正自己
- 失败时能**暂停并把控制权交还用户**
- 能访问工具与外部系统交互，**动态选工具**，始终在防护栏内

**反例**（不算 Agent）：简单聊天机器人、单轮 LLM、情感分类器——它们集成 LLM 但不用 LLM 控制流程。

## 2. 何时该构建 Agent

传统规则引擎像"检查清单"（按预设条件标记）；LLM Agent 像"经验丰富的调查员"（评估上下文、看细微模式、规则没违反也能识别可疑）。

优先用例三类：
| 类型 | 说明 | 例子 |
|---|---|---|
| 复杂决策 | 细微判断、异常、上下文敏感 | 退款审批 |
| 难以维护的规则 | 规则集庞大、更新贵易错 | 供应商安全审查 |
| 重度非结构化数据 | 自然语言、文档理解、对话 | 房屋保险理赔 |

> 提醒：用例不满足这些标准，就别用 Agent，确定性方案可能更合适。

## 3. Agent 设计三核心

```
Agent = 模型（Model）+ 工具（Tools）+ 指令（Instructions）
```

### 选模型
- 不同任务用不同模型：简单检索用小模型，复杂决策用大模型
- **推荐流程**：先用最强模型全任务做原型建基线 → 逐个换小模型看是否仍达标 → 成本/延迟优化
- 原则：① 建 evals 定基线 ② 优先用好模型满足准确率 ③ 能小则小

### 定义工具（三类）
| 类型 | 作用 | 例子 |
|---|---|---|
| 数据工具 | 检索上下文 | 查数据库、读 PDF、联网搜索 |
| 动作工具 | 采取行动 | 发邮件、更新 CRM、转人工 |
| 编排工具 | Agent 作为其他 Agent 的工具 | 退款 Agent、研究 Agent、写作 Agent |

**工具数量过载怎么办**：关键不是数量，而是**相似性/重叠度**。有的实现管 15+ 个区分明确的工具没问题，有的连 10 个重叠工具都难。先优化工具描述（名称/参数/说明），还不行就拆多 Agent。

### 配置指令（4 条）
1. **利用现有文档**：操作流程/客服脚本 → 转成 LLM 友好指令
2. **提示 Agent 分解任务**：把密集资源拆成更小更清晰的步骤
3. **定义清晰动作**：每步对应具体动作或输出，减少解释空间
4. **覆盖边界情况**：预判用户给不完整信息、问意外问题怎么办

## 4. 编排（核心）

> 重要建议：**渐进式**。别一上来就建复杂自主架构，客户经验表明渐进式更成功。

### 单 Agent：先尽量把一个 Agent 用足
- 单个 Agent + 逐步加工具能处理很多任务，保持复杂度可控
- "Run" 概念：Agent 在循环里跑，直到**退出条件**（调了最终输出工具 / 无工具调用直接回复 / 出错 / 达最大轮次）
- **Prompt 模板策略**：与其维护一堆独立提示词，不如用单一灵活基础提示词 + 策略变量（policy variables），新用例只改变量

**何时拆成多 Agent**：
| 场景 | 说明 |
|---|---|
| 复杂逻辑 | 提示词一堆 if-then-else 分支、模板难扩展 → 每段逻辑拆独立 Agent |
| 工具过载 | 工具描述优化后性能仍差 → 用多 Agent |

### 多 Agent 两种模式（重点）

**① Manager 模式（经理模式，集中式）—— 这就是你要用的**
- 一个中央 LLM（"经理"）通过**工具调用**编排专业 Agent 网络
- 经理不丢失上下文和控制权：分派任务、决定时机、合成结果
- 边 = 工具调用（在图中）
- 适用：只有一个 Agent 控制工作流、且是唯一与用户交互者的场景

**② Decentralized 模式（去中心化）**
- 多个 Agent 作为对等方，按专长**交接（handoff）**给彼此
- 边 = 交接（在图中）
- 适用：会话分流（triage），或希望专业 Agent 完全接管
- 例子：分流 Agent → 识别是售后问题 → 交接给技术支持 Agent

### 声明式图 vs 代码优先
- 声明式框架：提前显式画好所有分支/循环/条件，可视化清晰但复杂后笨重
- Agents SDK 做法：代码优先，用熟悉编程结构表达流程，支持动态自适应

## 5. 防护栏（Guardrails）

- **防御纵深**：单一防护栏不够，组合多个专用防护栏
- **关键类型**：
  - 相关性分类器（防离题）
  - 安全性分类器（防越狱/提示注入）
  - PII 过滤器（防泄露个人信息）
  - 内容审核（防有害内容）
  - 工具防护（按只读/写入/可逆性/财务影响给工具定风险等级，高风险动作暂停或转人工）
  - 规则保护（阻止列表、长度限制、正则）
  - 输出验证（防品牌/价值观偏离）
- **人工介入计划**：
  1. 超过失败阈值 → 升级人工（多次失败仍搞不清用户意图）
  2. 高风险操作 → 强制人工监督（取消订单、大额退款、付款）

## 6. OpenAI 结论

- 构建可靠 Agent 三要点：**强模型 + 好工具 + 清晰指令打基础；匹配复杂度的编排（先单后多）；防护栏贯穿全程**
- 成功部署不是"全有或全无"：从小处着手，真实用户验证，随时间增长能力

# 第三部分：对"桌边壁纸 Agent"项目的直接启示

两份文档正好互补：**Anthropic 讲透了"为什么拆、怎么拆、怎么汇总"，OpenAI 讲清了"编排模式怎么选、边界在哪"。**

结合你的项目，落地要点：

1. **编排模式确认**：你的项目就是 **Manager 模式（Orchestrator-Workers）**——壁纸里的编排 Agent 是唯一经理，WorkBuddy/Codex 是"工具化"的执行者。OpenAI 明确说这是"只有一个控制者、唯一与用户交互"时的正确选择。✅ 方案没选错

2. **子任务描述必须详细**（Anthropic 血泪）：拆出来的每个子任务要带【目标 + 输出格式 + 工具指导 + 任务边界】，否则子 Agent 会重复劳动。这是 P1 拆分 Prompt 设计的核心要求。

3. **规模分级**：直接在拆分 prompt 里写"简单任务 1 个 agent、比较类 2-4 个、复杂研究 10+ 个"，防止编排器拍脑袋乱拆。

4. **子 Agent 写文件系统**：你的 Codex/WorkBuddy 本来就该独立目录干活、只传回摘要——这正是 Anthropic 推荐的文件系统输出模式，坚持这个设计。

5. **Token 成本意识**：多 Agent 约 15× 聊天成本。你的场景（读长文/拆代码）价值高，但 P1 就要做"任务价值 vs 成本"的判断逻辑，别什么都拆。

6. **编码任务谨慎拆**（Anthropic 明确警告）："大多数编码任务可并行化部分少，LLM 实时协调不够好"。所以你的分工设计很对——**重代码派给 Codex 整块做，编排器只做轻代码（检查/运维）**，不要试图把一个大功能拆成 N 个小代码块并行写再合并，容易翻车。

7. **评估从小开始**：P1 用 20 个左右真实长任务做测试集，用 LLM-as-judge 打分，别用人肉看。

8. **防护栏**：自用阶段至少做输入长度限制、高风险操作确认（比如删除文件前问用户）。
